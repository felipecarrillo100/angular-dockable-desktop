# 11. Internationalisation

The library renders a few dozen strings of its own: tab tooltips, menu items, dialog text. It
translates none of them itself. The entire integration surface is one function.

## One function

```ts
import { provideDockableDesktop } from 'angular-dockable-desktop';

provideDockableDesktop({
  panels: { /* … */ },
  formatMessage: descriptor => translate(descriptor),
});
```

`formatMessage` is a `WorkspaceConfig` option (also accepted by `createWorkspace`), typed
`MessageFormatter`: `(descriptor: MessageDescriptor) => string`. A **message descriptor** is
`{ id, defaultMessage?, values? }`, where `values` is a `Record<string, string | number>`. Your
function receives it and returns a string. That is the whole contract — nothing is imported,
no locale is loaded, no format is assumed, and no Angular i18n package is required.

Anywhere the library accepts a label — a panel title, a modal title, a menu item, dialog text —
it accepts a `Label`, either a plain string or a descriptor:

```ts
workspace.openPanel('map', 'map', { title: 'Site plan' });
workspace.openPanel('map', 'map', { title: { id: 'panel.sitePlan', defaultMessage: 'Site plan' } });
```

A plain string is used as-is and never reaches your formatter.

### A locale in a signal

Angular re-renders what a template reads from signals. The library calls your formatter
inside its own templates, so if the formatter reads the current locale **from a signal**, a
locale change relabels every string the library renders — tab tooltips, title-bar buttons,
the unsaved-changes dialog, descriptor titles — with nothing to reopen and nothing to
re-register. This is the demo's whole integration (`projects/demo/src/app/locale.ts`):

```ts
import { signal } from '@angular/core';
import type { MessageDescriptor, MessageKey } from 'angular-dockable-desktop';

export type Locale = 'en' | 'es' | 'ar';
type Table = Record<MessageKey, string>;
declare const TABLES: Record<Locale, Table>;

export const locale = signal<Locale>('en');

export function formatMessage(descriptor: MessageDescriptor): string {
  const table = TABLES[locale()];                                  // read the signal here
  const key = descriptor.id.replace(/^ndd\./, '') as MessageKey;
  let text = table[key] ?? descriptor.defaultMessage ?? descriptor.id;
  for (const [name, value] of Object.entries(descriptor.values ?? {})) {
    text = text.replace(`{${name}}`, String(value));
  }
  return text;
}
```

```ts
bootstrapApplication(App, {
  providers: [provideDockableDesktop({ formatMessage, panels: { /* … */ } })],
});
```

`locale.set('es')` is then the only thing a language picker does. Falling back to
`defaultMessage` means a key you have not translated yet renders the library's English rather
than the raw id.

A formatter that reads a plain variable instead of a signal still translates, but a later
change to that variable is not seen until something else causes the view to refresh. If your
translation service keeps the language in an `Observable`, bridge it with `toSignal()` and read
that.

### A formatter that needs dependency injection

`provideDockableDesktop(config)` evaluates its config when the providers are built, outside
any injection context. When the formatter needs a service, provide the `Workspace` token
yourself:

```ts
import { DestroyRef, inject } from '@angular/core';
import { Workspace, createWorkspace } from 'angular-dockable-desktop';

export const workspaceProvider = {
  provide: Workspace,
  useFactory: () => {
    const i18n = inject(AppTranslations);          // your own service, exposing a signal
    const workspace = createWorkspace({
      panels: PANELS,
      formatMessage: d => i18n.translate(d.id, d.values) ?? d.defaultMessage ?? d.id,
    });
    inject(DestroyRef).onDestroy(() => workspace.dispose());
    return workspace;
  },
};
```

This is what `provideDockableDesktop(config)` does internally, with your factory in place of
its own.

### Without one

Omit `formatMessage` and the built-in fallback uses each descriptor's `defaultMessage`,
falling back to its `id`, and interpolates `{placeholder}` values. English out of the box, no
configuration.

## Formatting from your own code

`format` is a method on the workspace, so it works from a service, an interceptor or an error
handler:

```ts
workspace.format({ id: 'app.saved', defaultMessage: 'Saved {name}', values: { name } });
workspace.format(panelInfo.title);       // a string or a descriptor, whichever it is
```

It returns `''` for `undefined`. Call it on the workspace (`workspace.format(x)`) rather than
passing `workspace.format` around detached. `formatLabel(label, formatter?)` is the same logic
as a standalone export, for code that has no workspace to hand.

## Every title is a `Label`

`Label` is `string | MessageDescriptor`, and it is the type of the titles and labels the
library stores: panel titles (`openPanel`, the registry's `defaultOptions`, `PanelRef.setTitle`),
side-panel and modal titles, context-menu labels and tooltips, floating-widget titles, the
`<ndd-confirm>` message, and the `title` and `message` of `DirtyStateOptions`.

The rule behind that: **anything the library stores, it resolves on every render.** So a
descriptor handed to any of them follows a locale change on its own — while a string you
resolve yourself before handing it over is frozen at the language that was current at the
time, because the library has no way to resolve it again.

Toolbar items, sidebar tabs, rail entries and contributed sections take a plain `string`
`label`. They are data you pass on every change, so resolve them where you build the array,
inside something reactive:

```ts
protected readonly items = injectMergedToolbarItems((): ToolbarItem[] => [
  { type: 'action', id: 'save', label: this.ws.format({ id: 'app.save', defaultMessage: 'Save' }),
    icon: 'bi bi-save', onClick: () => this.save() },
]);
```

Because the getter runs inside a `computed`, and `format` calls your signal-reading formatter,
the toolbar relabels when the locale changes. Where the text comes from your own template —
an `<ndd-toolbar-button [title]>` tooltip, your panel's body — the choice does not arise: it
re-renders with your component either way.

## Overriding the built-in strings

Every string the library renders from its table is a descriptor with an `ndd.`-prefixed id —
`ndd.closeTab`, `ndd.minimizePanel`, `ndd.unsavedChangesTitle` and so on — and any subset can
be replaced:

```ts
createWorkspace({
  messages: {
    closeTab: { id: 'app.dismiss', defaultMessage: 'Dismiss' },
    unsavedChangesTitle: { id: 'app.unsaved', defaultMessage: 'Hold on' },
  },
});
```

The object is merged, so a partial override keeps every key it did not name. Two reasons to
reach for this rather than translating in `formatMessage`: to re-point a string at your own
message id, and to change the wording without touching translations at all.

`defaultMessages` is the built-in table, exported. `workspace.messages` is the merged table, if
you need to render one of the library's own strings in your own UI — a custom drawer header
that should say "Close" the same way the library does:

```ts
this.ws.format(this.ws.messages.closeTooltip);
```

For a compile-time guarantee that your own table covers every key:

```ts
import type { MessageKey } from 'angular-dockable-desktop';

const es: Record<MessageKey, string> = { /* … TypeScript names anything missing */ };
```

The keys are `floatWindow`, `minimizePanel`, `closeTab`, `restorePanel`, `maximizePanel`,
`closePanel`, `dockWindow`, `minimize`, `maximize`, `restoreSize`, `close`, `closeEmptyGroup`,
`emptyGroup`, `unsavedChangesTitle`, `unsavedChangesMessage`, `discardChanges`, `cancel`,
`yes`, `no`, `ok`, `closeTooltip`, `scrollTabsLeft`, `scrollTabsRight`, `moreActions` and
`search`; each id is the key prefixed with `ndd.`. `unsavedChangesMessage` carries a `{title}`
placeholder, which the library fills with the formatted title of the panel being closed.

Three accessible names are not in the table and render in English: the toast container's
"Notifications", a toast's "Close notification", and the sidebar drawer's close button.

## Reading direction

```ts
provideDockableDesktop({ dir: 'rtl', panels: { /* … */ } });
workspace.setDirection('rtl');       // at runtime
workspace.dir();                     // 'ltr' | 'rtl' — a signal
workspace.isRtl();                   // boolean — a signal
```

`dir` defaults to `'ltr'`. `setDirection` is a no-op when the direction is unchanged. A locale
and its direction usually change together; the demo derives one from the other in an effect:

```ts
effect(() => this.ws.setDirection(LOCALES.find(l => l.id === locale())?.dir ?? 'ltr'));
```

What mirrors automatically:

- **Drop zones** — the left target becomes the right one, and corner drop zones swap sides.
- **Tab order**, tab icons and close buttons in the tab strip, and the title-bar actions.
- **Corner anchors** for floating windows and inner widgets.
- **Resize handles** — a widget pinned to the inline end offers the handle on the opposite
  *physical* side, which flips with direction.
- **Side panels** — the left drawer opens from the right edge, and vice versa.
- **The context menu's** submenu chevron, checkbox column and submenu arrow keys (ArrowLeft
  enters a submenu under RTL).
- **Sidebar and toolbar edges**, through logical properties. The sidebar's resizer follows the
  side the drawer is physically on ([PARITY N6](../PARITY.md)), and a toolbar group's flyout
  opens by the strip's own computed direction ([N5](../PARITY.md)).

What does **not** mirror:

- **A free-floating window's position.** Its `x`/`y` are physical pixels, saved as such, so it
  stays where it was.
- **The saved layout.** A horizontal split's children keep their order and sizes in the
  layout tree; it is only the rendering, a flex row, that lays them out right to left. A layout
  saved in one direction loads unchanged in the other.
- **Your own content.** The library sets `dir` on its own chrome; inside a panel, direction is
  whatever your markup and CSS say, inherited from the nearest `dir`.

### Anchors are stored logically

This is the part worth knowing, because it affects saved layouts. An anchored floating window
records `top-left` / `bottom-right` and so on — but those names are **logical**: `left` means
inline-start. It is placed with `inset-inline-start` / `inset-inline-end`, so a layout saved in
RTL and restored in LTR puts every anchored window on the mirror-image side, which is the
correct reading of "it was at the start of the line".

If you need a window pinned to a physical side regardless of direction, do not anchor it —
give it an explicit rect.

### The `dir` attribute

The library sets `dir` on its own elements — the desktop, floating windows, modals, drawers,
the context menu, toolbar flyouts, the taskbar preview and inner widgets — so a nested `dir` on
your page is respected and the library never assumes the document direction. `workspace.dir()`
is what it uses. Chrome you own around the desktop does not follow it on its own; bind it:

```html
<div class="app-shell" [attr.dir]="ws.dir()">
  <ndd-sidebar [tabs]="tabs()">
    <ndd-desktop />
  </ndd-sidebar>
</div>
```

## `classes`, for a styling framework

Not strictly i18n, but the same shape of problem: reaching elements inside the library's own
markup. Six optional fields (`HostClasses`), added to the library's classes rather than
replacing them:

```ts
createWorkspace({
  classes: {
    modal: 'mat-elevation-z8',
    modalBody: 'p-4',
    sidePanel: 'shadow-xl',
    sidePanelBody: 'overflow-y-auto p-3',
    window: 'ring-1 ring-black/10',
    windowBody: 'bg-white',
  },
});
```

`workspace.classes` holds the resolved set, with every field present. The library's own
`ndd-` classes stay, so this adds to them. Those classes are also stable public names in their
own right — styling `.ndd-modal-body` directly is equally supported, and is the better choice
when the styling is CSS rather than utility classes ([chapter 10](10-theming.md)).

## Coming from vue-dockable-desktop

| vdd | ndd |
|---|---|
| `createWorkspace({ formatMessage })` | the same, or `provideDockableDesktop({ formatMessage })` |
| a formatter reading vue-i18n's reactive locale | a formatter reading a signal |
| `workspace.format()` / `formatLabel()` | the same |
| `workspace.messages` / `createWorkspace({ messages })` | the same |
| message ids `vdd.*` | `ndd.*` — the keys (`MessageKey`) are unchanged |
| `workspace.dir` / `workspace.isRtl`, refs | `workspace.dir()` / `workspace.isRtl()`, signals |
| `.vdd-modal-body` | `.ndd-modal-body` |

A message table keyed by `MessageKey` ports unchanged; one keyed by full id needs `vdd.`
replaced with `ndd.`.
