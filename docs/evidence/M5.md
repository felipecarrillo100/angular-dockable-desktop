# M5 — Floating windows · **PASS**

**Gate:** `npm run gate -- M5` (standing gate, M5 rules, browser gate). 355/355 unit tests.

## What exists

- **`ndd-floating-window`**: title bar (drag, double-click to maximise), maximise / minimise /
  close buttons (hidden per `canMinimize` / `canClose`), a body holding an `[nddPanelSlot]`, and
  8 resize handles (hidden while maximised).
  - **Positioning:** a free window is placed by physical `left`/`top`. An **anchored** window is
    placed by logical `inset-inline-start` / `-end`, driven by its own `dir`, so RTL mirrors it
    with no JavaScript. Windows sharing a corner stack with an 8 px inset and 8 px gaps.
  - **Focus and z-order:** focused chrome (`ndd-window-focused`) follows `activePanelId` (D2),
    and `ndd-maximized` matches its stylesheet rule (D9). A pointer-down anywhere in a window
    focuses it and raises its z-order.
- **Viewport clamp** on `<ndd-desktop>`: an effect over the measured workspace size and the
  window list, identity-guarded through `clampFloatingRect` (it writes to what it reads).
  Anchored windows have their size clamped; free windows have their position clamped too.
- **Typing:** strict templates caught an untyped union in the placement, which is now one
  `Placement` interface with every property nullable, so Angular removes unused ones.

Drag-to-dock from a title bar arrives with M6, and the title-bar context menu with M8.

## Browser gate (real Chrome, zoneless **and** zone.js)

- **Title-bar drag:** a real pointer drag moves the window by exactly (100, 60), and its size
  is unchanged.
- **D5, per handle:**
  - the handle's whole box lies **inside** the window (rdd's sat at −4 px, half clipped);
  - five points across the handle's own box all hit it (points outside the rounded corner are
    excluded, since they are not part of the window);
  - the first interior pixel of the edge hits it;
  - dragging it moves exactly the edges it serves by the pointer delta, and the others stay
    fixed.
- **D9:** a maximised window has computed `border-radius: 0` and `box-shadow: none`, fills the
  workspace, and has no handles.
- **Focus chrome** is on the active window only.
- **Survival:** the hosted panel was created once, never destroyed, and kept its WebGL context
  throughout.

**Negative control** (`m5.mjs --control`, run by M5's rules): inject rdd 6.2.0's handle
geometry. The gate must reject it, and does, on containment: "handle box … extends outside
the window, so part of it is clipped away".

## Findings

1. **The probes had to follow the box model.** The window has a 1 px border, so `right - 1`
   *is* the border while `left + 1` is already interior. The first interior pixel is
   `right - 2` / `bottom - 2`. A corner's extreme pixel lies outside the rounded corner, so
   corner handles are probed 4 px in on both axes. Neither is a library defect, and the
   coverage and containment checks above are what actually pin D5.
2. **The first D5 version could not have caught rdd's defect.** A −4 px handle still covers
   the first interior pixel. Containment and coverage were added, and the control proves they
   bite.
3. **The non-vacuity runner had a transient "no report" run** on its first M5 sweep; the
   identical run immediately after passed. It now retries once when no report appears (a stub
   that genuinely breaks the build still fails both runs). While adding that, an edit briefly
   removed the stale-report cleanup, which would have let one module inherit another's red. It
   was caught in review before any sweep ran with it, restored, and pinned by a selftest case
   (33 cases).

## M5's own rules (`scripts/gates/m5.mjs`)

1. Anchored placement uses `inset-inline-start` / `-end`, and nothing branches on direction.
